# Spec — Build Guard

Status: **engine ported, no UI.** The pure classification and lamp maths are in
and held to their generated vectors — 218 quest verdicts and 9 lamp cases, 81
tests green. Nothing is wired to the client yet: the four UI-facing stubs still
throw, and `SkeletonStubsTest` still holds them to it. See
`.claude/PLANNING.md` for the three decisions Milestone 1 settled.

## The product

A small plugin that warns before a quest, a lamp or an activity gives
experience that breaks an account's build — pures, zerkers, skillers, anything
deliberately capped. It is carved out of questpath-plugin, which already has
the engine; see `SOURCE-MAP.md`.

## Build restrictions are about XP, not levels

**A 1-Defence account is blocked by any quest that AWARDS Defence XP, whatever
its level requirements.** The check runs over the whole prerequisite chain.
Optional rewards and player-chosen lamps are not forced XP.

**Never resolve a conflict by loosening a rule.** If a verdict and a rule
disagree, the rule stands and the verdict is wrong.

## Scope, in this order

1. **Build rules UI, per skill.** Four types: no XP, hard cap, soft cap, goal.
   Show the XP headroom left under each cap.
2. **A verdict per quest, with its reason** — "blocked via Death Plateau:
   3,000 Attack XP".
3. **A warning when starting a build-blocked or unreachable quest.**
4. **Lamp advisor:** grey out blocked skills, box the suggested ones. The
   survey found questpath-plugin has the whole stack plus nine golden vectors,
   so **this is a port, not a stub** — `SOURCE-MAP.md` §7.
5. **Backlog**, in this order. `docs/TODO-build-guard.md` does not exist in
   questpath-plugin, so the brief's order governs:
   - attack-style warnings derived from build rules
   - Tears of Guthix warning and marker (it gives XP to your lowest skill)
   - lamp locking (consume clicks on blocked skills)
   - quest journal warnings
   - XP alarm when a no-XP skill gains any XP

## Out of scope

Shop run, diaries, routing, Quest Helper and Shortest Path hooks, website
sync, locked gear and max hits, themes.

## Open decisions

Not resolved. Do not close one by guessing.

- **How the plugin gets the quest graph.** Proposed: bundled at build time, as
  questpath-plugin does — generated by its `-export-quest-graph` and loaded
  from the jar. The bundle is 1.38 MB and carries shops, diary tasks and a
  1,301-row item catalogue that Build Guard has no use for; slimming it needs
  a new export flag in the Go app, not a change here. Decide: ship it fat,
  filter at build time, or add the flag.
- **How build rules are entered.** Presets (pure, zerker, skiller, …) or
  manual per-skill entry, or both. questpath-plugin has a manual editor only.
- **How the plugin reads quest completion state.** `Quest#getState` over
  `Quest.values()` on the client thread is what questpath-plugin does, matched
  **by name** rather than by id. Confirm that survives as the only source once
  the push is gone — and decide what happens to `QuestStatus.REFUSED`, which
  the plugin has no way to learn locally.
- **Hub review, and two plugins by the same author sharing logic.** Build
  Guard and questpath would both be on the Hub carrying the same ported
  engine. **Ask before submitting.**

### Raised while scaffolding, also open

- **The config surface is undecided.** The scaffold left the template's single
  `enabled` key in place rather than inventing one. Every key freezes on first
  publish, so settle this before anything ships.
- **What a verdict is allowed to say when no build rules exist.** With no
  rules nothing can be BUILD_BLOCKED, so every verdict is "as far as I know"
  rather than an answer. questpath-plugin's `rulesKnown()` exists for exactly
  this and its wording assumed a sync that Build Guard will not have.
